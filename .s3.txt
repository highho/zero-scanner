【根因定位：CONTEXT 缓冲区 16 字节对齐（已修复并提交）】
- 现象复现：app 目录下 `ZERO_DBG_TRACE=1 ./target/debug/zero-scanner.exe --dbg-test` → PASS 靶场/已附加，FAIL 写入断点命中 0 次，FAIL detach 无错误 (Some("所有线程都写不进断点（6 个失败）"))。单次运行约 50 秒（含 45 秒 deadline）。
- dbg_trace.log 揭示关键一行：`apply: thread 3336 suspend=0` 紧接着 `apply: GetThreadContext 3336 failed err=998`，其余 5 个线程 suspend=1 同样 998。即 SuspendThread 成功、GetThreadContext 仍报 998 ERROR_NOACCESS。
- 根因：`GetThreadContext` / `SetThreadContext` 要求 CONTEXT 缓冲区按 **16 字节对齐**。原代码 `let mut ctx: CONTEXT = std::mem::zeroed();` 是栈上局部变量，编译器只保证 8 字节对齐；栈帧布局随任何无关改动（加一行诊断、改版本号、加一个 cargo feature）变化就可能落到非 16 字节边界 → API 立刻 998。这解释了「换个构建就全不命中、git stash 回去又好了」的诡异现象。
- 修复（app/src/debugger.rs，替换原 read_context_with / write_context_with 区块，位置约 line 550-590）：新增
  - `#[repr(C, align(16))] struct AlignedX64(CONTEXT);` 与 `#[repr(C, align(16))] struct AlignedX86(WOW64_CONTEXT);`
  - `fn x64_get(handle: HANDLE, flags: u32) -> Option<CONTEXT>` / `fn x64_set(handle: HANDLE, flags: u32, ctx: &CONTEXT) -> bool`
  - `fn x86_get(handle: HANDLE, flags: u32) -> Option<WOW64_CONTEXT>` / `fn x86_set(handle: HANDLE, flags: u32, ctx: &WOW64_CONTEXT) -> bool`
  - 这四个 helper 内部都先 `let mut holder = AlignedX64(...)` / `AlignedX86(...)` 再取 `&mut holder.0`，把对齐变成类型属性而不是运气。
  - `read_context_with(handle, is_64bit)` / `write_context_with(handle, is_64bit, ctx)` 改为只做分支转发到上述 helper。
- 同步把另外两处裸调用改为走 helper：`read_thread_context`（原 CONTEXT_ALL_AMD64 / WOW64_CONTEXT_ALL）改为 `x64_get(handle, CONTEXT_ALL_AMD64).map(SavedCtx::X64)` / `x86_get(...)`，CloseHandle 移到之后；`write_thread_context(_target, thread_id, ctx)` 改为 `write_context_with(handle, _target.is_64bit, ctx)`；`write_thread_context_saved` 签名改为 `fn write_thread_context_saved(is_64bit: bool, thread_id: u32, original: &SavedCtx) -> bool`（目前无调用点，仅为一致性）。
- 验证：`cargo build` 后 `--dbg-test` 全 PASS —— 靶场已就绪 pid=27348 addr=0x29AC75C5110 / 已附加 / **写入断点命中 3 次** / 命中带 RIP 0x7FF62483EB4E / 命中记录指令字节 / 命中读回写入值 / detach 无错误 (None) / detach 后目标仍存活 / RESULT: PASS。
- 全量 selftest：**160 PASS / 0 FAIL**，RESULT: PASS（含 9 条 debugger 断言）。
- 教训：**cargo check 不产出 exe**，改完必须 `cargo build` 再跑测试；否则跑的仍是旧二进制，会误判修复无效。

【环境坑（复用）】
- run_code 内联含 `++` 报 `Expected ',', got '++'`；内联含反引号会截断模板字面量报 `Expected a semicolon` / `Expected ',', got '{'` —— 长代码用数组 join 或 write 工具写文件再跑。
- 长命令（3 次连跑 dbg-test 各 50 秒）会超 run_code 默认 120s 上限，需拆开或加 timeoutMs。
- `cargo build` 报 `failed to remove file ... target\debug\zero-scanner.exe: 拒绝访问 (os error 5)` = 有 zero-scanner 进程在跑，先 `powershell -NoProfile -Command "Stop-Process -Name zero-scanner -Force -ErrorAction SilentlyContinue"`。
- selftest 与 dbg-test 的日志写在**当前工作目录**（selftest.log / dbg-test.log / dbg_trace.log），不是项目根。
- 直接调用 read/grep/glob 必须在 run_code 里 await tools.xxx。
